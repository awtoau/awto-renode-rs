# Review: making Rust more C#-like, and knowing what to port before porting it

Five proposals, reviewed against what the corpus actually measures and what the
four research reports found. Written as a review, so where I disagree I say so
and show the number.

Short version: **(3) is already started and should go further, (4) is the
strongest idea here and nobody in the literature has done it for C#, (1) and
(2) are right in principle but the surface is far smaller than it looks, and
(5) falls out of (4) for free.**

---

## The measurement that reframes (1) and (2)

The proposal is to add a GC type to `csharp-rt` so the initial port is
mechanical. Before sizing that, here is what the cut actually contains:

| | count |
|---|---|
| instance fields | 552 |
| primitives and `string` | 210 |
| register-field handles (`IFlagRegisterField`, `IValueRegisterField`) | 84 |
| **fields whose type is another corpus object** | **~30** |

The register handles are the biggest group of "reference-typed" fields and
**none of them need a GC** — D2 already makes them typed indices into an arena,
which is exactly the strategy the GC literature recommends for this shape.

So the genuinely GC-shaped surface is roughly: `IMachine` (6), `IBusController`
(4), `IPeripheral` (2), plus a handful of peripheral-to-peripheral links. Call
it **thirty fields**, not 342.

**This does not kill the idea, but it changes what it is for.** A `Gc<T>` is not
needed to make the bulk of the port mechanical — the bulk is primitives,
register handles and collections, all of which already translate. It is needed
for one specific thing: **the machine ↔ peripheral cycle**, which is the exact
case D1 already calls out and currently answers with "leak it".

### Verdict on (1) and (2)

Worth doing, but as a **narrow type, not a general GC**, and the reason is in
the research:

- `Rc<RefCell<T>>` leaks cycles, and D1 accepts that deliberately: the machine
  is built once and lives for the process. For thirty fields in a process that
  exits, **leaking is not a bug** — it is the correct answer, and a tracing GC
  would be machinery bought to solve a problem we do not have.
- `safe-gc` proves a real tracing GC can be built in Rust with
  `forbid(unsafe_code)` — and its author states plainly it "is not a
  particularly high-performance garbage collector".
- Every surveyed design (`rust-gc`, `gc-arena`, `shifgrethor`, Josephine) pays
  its cost in **rooting discipline**, which is exactly the thing that would make
  the port *less* mechanical, not more.

What I would build instead, and it is small: a `Handle<T>` in `csharp-rt` that
is `Rc<RefCell<T>>` with a `Weak` back-edge variant, so back-references are
spelled explicitly and cycle-leaking is a visible choice per field rather than
a blanket policy. That is the same shape as Bun's `LIFETIMES.tsv` classes —
`OWNED`/`SHARED`/`BACKREF` — which is the one production example we have of
this working at scale.

The general principle behind (2) — **make Rust more C#-like for the initial
port, then lift** — is right, and `csharp-rt` already exists for it. `Array2D`
was the first entry precisely because the approximation was observably wrong.
The bar stays: a type earns its place when the approximation is *observably*
different, not when it is merely inconvenient.

## (3) Rewrite C# into a simpler form first

**Already started, and it should go much further.** The normalisation phase
landed today: ordered passes, run to a fixpoint, capped, with the first pass
turning `x?.Foo();` into an if-guard. That single rewrite unblocked
`STM32_UART.Reset` without needing any nullability analysis, because the
rewrite is exact in statement position.

The literature is unanimous that this is the right layer:

- **CROWN** inserts explicit null assignments into the C *before* translating,
  to make ownership monotone.
- **py2many** runs rewriter passes over the AST before backend dispatch.
- **Scylla** goes furthest and has the *programmer* restructure the C until it
  is eligible — which is closed to us, since we cannot edit Renode.

Candidates visible in the current gap and error lists, each an exact rewrite
rather than a mapping:

| rewrite | why it is exact |
|---|---|
| `x ?? y` → `if x is null then y else x` | same short-circuit, no new concept |
| `a[i, j]` → `Array2D::get` | done, via `csharp-rt` |
| compound assignment → binary + assign | already derived from the binary table |
| `foreach` over a dictionary → explicit iterator | removes the ordering question |

**The discipline to keep:** a normalisation must be *exact*, not merely
plausible. The `?.` pass is exact in statement position and refuses expression
position for that reason. A rewrite that is "close enough" is worse than a
mapping, because it launders a deviation into a shape nothing will question.

## (4) Prescan to find out what actually needs GC — the strongest idea here

This is the one I would build next, and **no surveyed project has done it for
C#**.

The proposal: analyse the running C# to learn which objects are actually
shared, actually cyclic, and actually long-lived — rather than assuming from
the type system that every reference might be.

The literature backs the method from three directions:

- **c2rust-analyze** builds a Pointer Derivation Graph by *instrumenting and
  running* the program, then feeds it into a static permission lattice. Its own
  issue tracker records the limitation this fixes: the static analyser is
  flow-insensitive, so "one null store anywhere poisons the whole declaration".
- **depyler's ancestor `pyrs`** used MonkeyType — run the program, record the
  types, feed them to the translator. Dynamic analysis supplying what static
  analysis cannot.
- **Bun** precomputed a per-field ownership ledger with an `evidence` column
  and a legal `UNKNOWN`, and instructed its agents to "trust it over local
  guessing".

**What makes it unusually tractable here**: we can already run C# Renode, and
we already capture traces from it. The instrumentation point exists. And C#
gives us something C does not — the runtime *knows* the object graph, so
reachability, sharing and lifetime are observable rather than inferred.

Concretely, a prescan would emit one row per field:

    type · field · class · evidence · touched · shared · cyclic

with `class` in `OWNED | SHARED | BACKREF | ARENA | UNKNOWN`, and `UNKNOWN`
legal. That is Bun's schema, and it is the artefact that makes the ownership
decision *per-site with recorded evidence* rather than a global policy — which
all four research reports independently identified as the thing every working
system does.

**It also answers the refactor question directly.** "Should this be refactored
before conversion" becomes a query — a field touched from thirty call sites
across four types is a different problem from one touched twice, and right now
we cannot tell them apart.

**Caveat, and it is the same one as everywhere else**: dynamic evidence is only
as good as the paths exercised. A field that is never null *in the traces we
ran* is not a field that is never null. The prescan must record coverage
alongside the classification, or it becomes another confident-and-wrong input.

## (5) A top-level model of the code

Falls out of (4) nearly for free, and is cheap independently — the corpus
database already holds types, members, base links and call sites. A Mermaid
diagram of the peripheral graph, the inheritance chains, and the ~30
object-reference edges is a query, not a project.

Worth doing precisely *because* the number is 30. A diagram of 30 edges is
readable and would show at a glance which are cycles — which is currently
knowledge nobody has, including me. I have been reasoning about "the object
graph" all session without ever having seen it.

---

## What I would do, in order

1. **The prescan (4)**, because it is the only item that produces evidence
   rather than consuming it, and because everything else — the GC decision, the
   refactor question, D1's arena lift — is currently being decided without it.
2. **The model (5)**, immediately after, since it is the same data.
3. **More normalisations (3)**, continuously; they are cheap and each is exact.
4. **`Handle<T>` in `csharp-rt` (1, 2)** *after* the prescan says which fields
   are `SHARED` versus `BACKREF`. Building it first means guessing the thing the
   prescan would tell us.

## What I would not do

Add a tracing GC. Thirty fields, in a process that builds its object graph once
and then exits, do not justify rooting discipline — and the rooting discipline
is precisely the part that would make the port *less* mechanical, which is the
opposite of the stated goal.
